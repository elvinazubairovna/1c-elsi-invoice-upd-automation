# Порядок разработки и аудита

1. Владелец получает от ChatGPT готовый файл задания `NNN_TASK_NAME.md` и помещает его в `DEV/tasks/`.
2. До любых действий Codex полностью читает корневой `AGENTS.md`, затем точный файл задания. После этого проверяет активное состояние Git, ветку, базовый SHA и разрешённые пути. Посторонние пользовательские файлы и изменения сохраняются и не включаются в коммит.
3. Если требуемое техническое решение отсутствует, конфликтует с инструкциями или потребовало бы самостоятельного выбора, Codex останавливается со статусом `BLOCKED` и передаёт вопрос владельцу для решения ChatGPT.
4. Codex реализует только разрешённые изменения и запускает проверки из задания. Статус указывается честно: `SUCCESS`, `PARTIAL`, `BLOCKED` или `FAILED`.
5. **Обязательная сверка документации после тестов и до отчёта/коммита:**
   - сравнить требования и фактический diff с `README.md`, `DEV/docs/ARCHITECTURE.md`, `DEV/docs/REQUIREMENTS.md`, `DEV/docs/SECURITY.md`, этим workflow и другими актуальными документами;
   - обновить затронутые документы, конфигурацию, ограничения безопасности и пользовательские инструкции в той же задаче;
   - добавить фактический changelog entry и синхронизировать implementation status на основании проверяемых свидетельств;
   - проследить цепочку `task → implementation → tests → documentation → report`; неподтверждённые утверждения пометить `UNVERIFIED`/`NOT_IMPLEMENTED`;
   - включить в отчёт матрицу `Documentation reconciliation`: документ, просмотр, изменение и причина, фактическая проверка, расхождения и их решение;
   - при противоречии, требующем решения архитектора, не публиковать и не заявлять `SUCCESS`; остановиться со статусом `BLOCKED`.
6. Создать `DEV/reports/NNN_TASK_NAME.md` с перечнем изменённых файлов, точными командами и результатами проверок, ограничениями и отклонениями, Git status, статусом публикации, ссылкой на отчёт и SHA, известными при написании. Не публиковать персональные данные, секреты и подробные значения срабатываний. Не указывать SHA коммита, содержащего этот отчёт, как известный заранее.
7. Перед коммитом просмотреть список файлов, staged diff и результат `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Index`. Перед push проверить все отправляемые версии файлов через `-Mode Outgoing`. Локальные hooks помогают, но могут быть отключены или обойдены; ручные проверки обязательны.
8. После успешного коммита и push Codex сообщает владельцу итоговый удалённый HEAD SHA и ссылку на отчёт. Если отчёт входит в этот коммит, не создавать дополнительный коммит только ради вписывания его SHA в сам отчёт. Новые docs публикуются вместе с соответствующими изменениями, не позднее.
9. Только ChatGPT проводит аудит результата и устанавливает `ACCEPTED`, `REWORK_REQUIRED` или `BLOCKED`. Codex не объявляет аудит завершённым и не начинает следующую задачу самостоятельно.

Заблокированная до изменений задача может требовать только правдивого отчёта: не создавайте фиктивную успешную запись в `CHANGELOG.md`. Для завершённой задачи changelog всегда отражает фактическую работу, в том числе документационную и процессную.

## Обязательная сверка документации перед отчётом и коммитом

После реализации и тестов, но до отчёта и коммита, для каждой задачи выполните отдельную сверку:

1. Сопоставьте требования задания и фактический diff с канонической документацией: `README.md`, `DEV/docs/ARCHITECTURE.md`, `DEV/docs/REQUIREMENTS.md`, `DEV/docs/SECURITY.md`, настоящим workflow и остальными актуальными документами.
2. Обновите документы, описывающие реально изменённые функции, конфигурацию, ограничения безопасности и пользовательские процедуры. Документы публикуются вместе с соответствующими изменениями, а не обещаются на будущее.
3. Добавьте фактическую запись по завершённой задаче в `DEV/docs/CHANGELOG.md`; синхронизируйте `DEV/docs/IMPLEMENTATION_STATUS.md` только с подтверждёнными свидетельствами. Если категория статуса не изменилась, повторно проверьте её и явно укажите это в отчёте.
4. Проследите цепочку `task → implementation → tests → documentation → report`. Неподтверждённые утверждения помечайте `UNVERIFIED` или `NOT_IMPLEMENTED`. Если устранение противоречия требует архитектурного решения, остановитесь со статусом `BLOCKED` и запросите решение через владельца проекта.
5. В отчёте добавьте таблицу `Documentation reconciliation`: для каждого изученного документа укажите, был ли он просмотрен, изменён ли и почему, на каких фактах основана проверка, и есть ли расхождения.
6. Если задача заблокирована до изменений, составьте правдивый отчёт, но не создавайте фиктивную успешную запись в changelog.

В отчёте не публикуйте чувствительные данные, даже если они встретились в локальной среде. Завершение документационной сверки не означает архитектурную приёмку: статус `ACCEPTED` назначает только ChatGPT.

## Локальные проверки

- До коммита: `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Index`.
- До push: `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Outgoing` с теми же ref updates, которые будут отправлены.
- Проверки безопасности: `pwsh -NoProfile -File tests/security/Invoke-SecurityTests.ps1`.

Проверки анализируют известные опасные файлы и шаблоны, но не гарантируют отсутствие всех конфиденциальных данных. Ручной аудит содержимого обязателен. GitHub Actions проверяет опубликованное состояние и не предотвращает первое раскрытие в публичном репозитории.
