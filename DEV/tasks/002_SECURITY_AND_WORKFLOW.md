## 1. Цель

Подготовить воспроизводимый и проверяемый процесс публикации изменений в GitHub, снизить риск случайной публикации реальных бухгалтерских файлов, персональных данных и секретов, а также формализовать цикл **задание → реализация → отчёт → GitHub → аудит ChatGPT**.

Создать локальные проверки на Windows, их автоматический запуск в GitHub Actions и тесты положительных и отрицательных сценариев. Подчеркнуть в документации: **автоматические проверки не гарантируют отсутствие всех конфиденциальных данных**; ручной аудит содержимого коммитов обязателен. GitHub Actions запускается **после публикации** и не предотвращает первоначальное раскрытие информации в публичном репозитории.

## 4. Правила безопасности и классификации

### 4.1. Что **нельзя** публиковать

Реальные счета, УПД, договоры, акты, Excel-реестры, выгрузки/резервные копии 1С; реальные сведения о контрагентах и физических лицах (ИНН/КПП, банковские реквизиты, адреса объектов, суммы, паспортные данные, телефоны, email); учетные данные, `.env` с секретами, токены, ключи, сертификаты/закрытые ключи ЭЦП, пароли; локальные пути и настройки, раскрывающие чувствительную информацию. Также не публиковать эти сведения в заданиях, отчётах, логах, тестах и примерах.

Для тестов допустимы **только заведомо синтетические сведения**, не воспроизводящие реальные документы, реквизиты и персональные данные.

### 4.2. `.gitignore`

Сохранить существующие исключения и добавить покрытие как минимум для следующих категорий независимо от регистра расширения (где возможно):

- бухгалтерские документы: `pdf`, `xls`, `xlsx`, `doc`, `docx`, `csv`;
- базы и выгрузки 1С: `dt`, `1CD`, а также резервные копии `bak`, `backup`;
- сертификаты и приватные ключи: `key`, `pem`, `pfx`, `p12`;
- архивы `zip`, `rar`, `7z` как потенциальные носители реальных данных;
- `.env` и `.env.*` (исключение для безопасного шаблона `.env.example`);
- каталоги с чувствительным содержимым **на любой глубине**: `private`, `secrets`, `backups`, `exports`, `data/real`;
- типовые локальные конфигурации и временные файлы, если их безопасно определить без блокировки разрешённого исходного кода.

Не полагаться на `.gitignore`: уже отслеживаемые файлы он не защищает.

### 4.3. Проверка публикации `DEV/tools/Test-Publication.ps1`

Один основной скрипт с параметром `-Mode`, принимающим строго `Index`, `Tracked`, `Outgoing`:

- **Index:** проверить весь состав текущего Git index (не только worktree) перед коммитом. Сканировать содержимое именно индексированных версий файлов; считать ошибкой неоднозначный путь/невозможность чтения.
- **Tracked:** проверить весь состав файлов текущего отслеживаемого дерева Git; использовать для CI на чистом checkout, проверяя файлы, включённые в commit, а не локальные неотслеживаемые файлы.
- **Outgoing:** до `push` проверить **все вновь отправляемые коммиты и версии файлов в них**, включая файл, добавленный и удалённый следующим коммитом. Использовать пары локальной и удалённой ссылок, предоставляемые `pre-push` через stdin; при невозможности достоверно определить публикуемый диапазон **блокировать публикацию**. Не ограничиваться проверкой последнего `HEAD`.

Все режимы должны иметь одинаковые политики. Провести достаточный анализ Git-файлов/объектов с корректной обработкой пробелов и Unicode в путях. Если нельзя гарантировать корректный разбор спецсимволов в путях, отклонять такие неоднозначные случаи безопасно (`fail closed`), а не пропускать проверку. Не обходить ошибки Git или неуспешный код возврата.

Минимальные политики проверки:

1. Отклонение любого отслеживаемого файла запрещённого расширения или запрещённого каталога, включая файлы, добавленные `git add -f` несмотря на `.gitignore`.
2. Отклонение секретов с высокой уверенностью: заголовок PEM private key; типовые GitHub, облачные и OpenAI API-токены с характерной структурой; распространённые явные присваивания секретов (`password`, `token`, `api_key`, `secret`) с непустым неплейсхолдерным значением. Не сохранять/печатать найденные значения.
3. Поиск структурированных российских ИНН на 10/12 цифр с проверкой контрольных цифр; в случае совпадения **блокировка** и сообщение о типе находки без вывода значения. Исключения для реальных ИНН запрещены. Числа в коммитах, SHA и обычной документации не должны ошибочно интерпретироваться без границ токена и валидации.
4. Блокировать попытку включить явно реальные счета/акты или реестры, даже если расширение файла неожиданное; простой эвристический поиск в текстовых файлах допустим как дополнительная страховка, но не единственный барьер.
5. Не сканировать по сети, не загружать данные в сервисы и не выдавать потенциально чувствительные фрагменты в вывод. В выводе только `PASS/FAIL`, тип правила, путь (если сам путь не содержит чувствительных значений — иначе маскировать), количество срабатываний и код возврата.
6. Возврат **0** только при успешной проверке; ненулевой код для нарушения, сбоя чтения, неустановленного Git или некорректного режима.
7. В `.md`-документации, содержащей названия правил, не должно возникать ложного срабатывания от безопасного описания без реального секрета.

**Ограничение:** анализ текстовых файлов не даёт гарантий для всех типов персональных данных и закодированных секретов. Для бинарного файла, который проверяющий не умеет анализировать безопасно, применить консервативный запрет на публикацию до отдельного разрешения архитектора. Не устанавливать автоматически разрешающие исключения для нераспознанных форматов.

### 4.4. Локальные hooks

- `DEV/hooks/pre-commit`: запуск `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Index`; при ошибке запрещать коммит.
- `DEV/hooks/pre-push`: запуск `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Outgoing`; передать stdin с обновляемыми ref и корректно обработать отсутствие информации. При ошибке запрещать push.
- `DEV/tools/Install-LocalHooks.ps1`: только локальная настройка `git config --local core.hooksPath DEV/hooks`. Сначала проверить старое значение `core.hooksPath`. Если оно нестандартно/указывает на существующий иной набор hooks, **не заменять** его молча: `BLOCKED`, инструкция для владельца. Не затрагивать `.git/hooks` глобально, не удалять существующие hooks. После установки подтвердить Git config и работоспособность.
- Hooks **могут быть отключены или обойдены**, поэтому `AGENTS.md` отдельно требует ручной вызов проверок до `git commit` и `git push`. При отсутствии/ошибке `pwsh` обе операции должны блокироваться.

### 4.5. GitHub Actions

Создать `.github/workflows/publication-security.yml`:

- события `push` (ветка `main`), `pull_request` (цель `main`), `workflow_dispatch`;
- единственный job с уникальным названием `publication-security`;
- `runs-on: ubuntu-latest`;
- права `permissions: contents: read` на уровне workflow;
- `actions/checkout@v7` с `persist-credentials: false` (официальное действие; без других сторонних actions);
- шаги: проверка наличия `pwsh`, `pwsh -NoProfile -File DEV/tools/Test-Publication.ps1 -Mode Tracked`, `pwsh -NoProfile -File tests/security/Invoke-SecurityTests.ps1`;
- никаких токенов, секретов, `pull_request_target`, команд публикации, автоматических исправлений или сетевой отправки содержимого;
- ошибки проверок должны делать job красным. CI не заменяет до-публикационный контроль.

Если использование `actions/checkout@v7` технически невозможно в целевой среде, остановиться и документировать ограничение; не заменять версию самостоятельно без архитектурного согласования.

## 5. Испытания — обязательно

`tests/security/Invoke-SecurityTests.ps1` должен запускать проверки в **изолированных временных Git-репозиториях вне проекта**, создавать **только вымышленные** тестовые файлы, удалять временные каталоги после завершения и не выполнять `push` в настоящий GitHub. Проверять минимум:

1. Разрешённый `.md` без секретов → `PASS`.
2. `pdf`/`xlsx`/`csv`, принудительно добавленные в index → `FAIL`.
3. Файл внутри вложенного `secrets/` → `FAIL`.
4. Контент с **синтетическим, формально похожим на токен** значением → `FAIL`, без вывода значения.
5. Контент с синтетическим корректным по контрольным цифрам ИНН → `FAIL`, без вывода номера.
6. Текстовое описание правила `api_key` без реального присваивания → `PASS`.
7. Добавлен, а затем удалён запрещённый файл в двух последовательных коммитах → `Outgoing FAIL` при проверке этих коммитов, хотя в HEAD файла нет.
8. Неоднозначный ввод, ошибка Git или неразрешённый режим → `FAIL`.
9. Тесты должны самостоятельно проверять коды возврата и завершаться ненулевым кодом при любом несовпадении.
10. Проверить, что обычный текущий репозиторий проходит `Index` и `Tracked`, при этом тестовые чувствительные файлы **не попадают в реальный index**.

Если изолировать тестовые репозитории невозможно, не заменять тесты изменением реального index — пометить `BLOCKED`.

## 6. Регламент `DEV/docs/DEVELOPMENT_WORKFLOW.md`

Документировать чёткий цикл:

1. Владелец получает от ChatGPT **готовый файл** `NNN_TASK_NAME.md` и кладёт в `DEV/tasks/`.
2. Codex читает `AGENTS.md`, указанную задачу, выполняет только её; при неизвестном решении останавливается.
3. До работы проверяет Git state и сохраняет посторонние пользовательские файлы; никаких чужих исправлений.
4. Делает разрешённые изменения и тесты; фиксирует честный статус `SUCCESS`, `PARTIAL`, `BLOCKED` либо `FAILED`.
5. Перед коммитом проверяет index, staged diff, список файлов и политику конфиденциальности. Перед публикацией проверяет **все outgoing commits**.
6. Заполняет `DEV/reports/NNN_TASK_NAME.md` с перечнем изменённых файлов, точными выполненными командами тестов и их результатами, ограничениями, отклонениями, status Git, статусом публикации, ссылкой на GitHub и значимыми SHA.
7. В отчёте **не вписывать SHA коммита, содержащего этот самый отчёт, как будто он был известен заранее**. Вместо этого указывать исходный SHA, известные уже созданные коммиты и отдельно возвращать окончательный удалённый HEAD SHA в сообщении владельцу; не создавать бесконечную цепочку «коммит ради обновления SHA отчёта».
8. После успешного коммита/публикации Codex сообщает владельцу итоговый SHA и ссылку на отчёт. Только ChatGPT проводит аудит и ставит `ACCEPTED`, `REWORK_REQUIRED` или `BLOCKED`.
9. Запрещено самовольно начинать следующую задачу; Codex не объявляет аудит завершённым сам.
10. Публикация отчёта разрешена только после удаления из него персональных данных, секретов и подробных значений срабатываний.

Дополнить `AGENTS.md` этими обязательствами без удаления уже имеющихся правил. Добавить в `README.md` короткую ссылку на регламент.

## 9. Отчёт Codex

В `DEV/reports/002_SECURITY_AND_WORKFLOW.md` использовать структуру:

- `Status` — `SUCCESS` / `PARTIAL` / `BLOCKED` / `FAILED`.
- `Base state` — исходный SHA/ветка/состояние пользователя.
- `Changed files` — точный список.
- `Security model` — что блокируется и чего нельзя гарантировать.
- `Checks and tests` — команды, PASS/FAIL, отдельные отрицательные сценарии.
